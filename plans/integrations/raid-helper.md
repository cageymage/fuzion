## 2. Webhooks

### 2.1 How a webhook is configured
- The Discord slash command `/webhooks show` returns a "webhook key" generated by Raid-Helper (not chosen by the server admin). Format: a 30-character alphanumeric string. The value is deliberately not recorded in this repo. VERIFIED that the command exists and issues a key.
- Discord's command picker lists four `/webhooks` subcommands (VERIFIED, from a screenshot):
  - `/webhooks show`: "Show all webhook urls and your secret key."
  - `/webhooks refresh-key`: "Generate a new authorization key for your webhooks."
  - `/webhooks set`: "Set a webhook url."
  - `/webhooks reset`: "Reset a specific webhook url."
- `/webhooks set` has a `type` choice with four values (VERIFIED, from the command picker): `event.create`, `event.update`, `event.delete`, `comp.update`. Each type presumably has its own URL. Note these are the command's option names. The `type` string inside the request body may differ (the ticket assumed `event.created`/`updated`/`deleted`): `TODO`.
- `comp.update` is not in the ticket. "comp" probably means composition (the roster of signups), so it may fire when someone signs up, changes spec or leaves. If so, it could tell us when signups change. `TODO`: when it fires and what its body carries.
- After `/webhooks set` was run for each of the four types, `/webhooks show` listed the same key against every type. So there is one key per server, shared by all four webhook types (VERIFIED). A single check on our side covers all of them.
- Capture attempt 1 (VERIFIED negative result): all four types were set to a webhook.site address, and `/webhooks show` confirmed all four URLs were saved. webhook.site itself was confirmed working (two manual curl POSTs were recorded). Then, in the test server: a new event was created, an event was edited, a signup was added and withdrawn, and an event was deleted. **No request arrived for any action.** Cause undetermined. The plural "webhook urls" suggests more than one configurable URL, probably per event type. Arguments of `set` and `reset`: `TODO`.

## 3. Event object and signups

### 3.1 Endpoint
- **Request:** `GET https://raid-helper.xyz/api/v4/events/{eventId}`, e.g. `.../api/v4/events/1556072183254622279`. The event page on the Raid-Helper website has a direct link to this JSON.
- **Response:** `200`, `Content-Type: application/json;charset=utf-8`, and it is valid JSON. The sample originally pasted looked like JS-object notation because of how it was displayed, not because of the wire format. Display names with quotes arrive correctly escaped (e.g. `Zarik\"OhioAssWarlock\"Envy`).
- **Auth:** none needed for this event. It was fetched with no cookies, API key or Authorization header, so it is a public GET by event ID. Whether this holds for all events (e.g. servers that restrict visibility), `TODO`.
- **Host and version:** the link uses `raid-helper.xyz` and `v4`. The docs site is `raid-helper.dev`, and third-party code was seen using `.dev/api/v2/...`. Whether `.xyz`/`.dev` and v2/v4 are interchangeable or versioned differently: `TODO`.
- **Response headers** (captured with `curl -i`, anonymous request):
  ```
  HTTP/1.1 200 OK
  Server: nginx/1.18.0 (Ubuntu)
  Content-Type: application/json;charset=utf-8
  Transfer-Encoding: chunked
  Vary: Accept-Encoding
  Access-Control-Allow-Origin: *
  Access-Control-Allow-Credentials: true
  Access-Control-Allow-Methods: GET, POST, PUT, DELETE, OPTIONS
  Access-Control-Allow-Headers: Content-Type, Authorization, X-Requested-With, withCredentials, serverid
  auth-debug: event1-<client IP, redacted>
  ratelimit-bucket: event1
  ratelimit-limits: [{"limit":20,"reset":0,"window":5,"remaining":19},{"limit":100,"reset":40,"window":60,"remaining":97},{"limit":400,"reset":400,"window":600,"remaining":397},{"limit":2000,"reset":1600,"window":3600,"remaining":1995},{"limit":10000,"reset":19600,"window":86400,"remaining":9995}]
  ```
- **Rate limits (anonymous):** bucket `event1`, five stacked windows: 20 requests per 5 s, 100 per 60 s, 400 per 10 min, 2,000 per hour, 10,000 per day. `remaining` fell as expected between calls. It looks keyed on client IP (the `auth-debug` header echoes the caller's IP), so a server-side fetch from our API would share one budget across all Calendar visitors. Meaning of `reset` (seconds until the window resets?) is inferred, `UNVERIFIED`. Whether an API key or `Authorization` header raises these limits: `TODO`.
- **CORS:** `Access-Control-Allow-Origin: *`, so a browser on any site can call this endpoint directly. The allowed request headers include `Authorization` and a custom `serverid`, which suggests optional authentication and a server-ID header exist, but what they do is `TODO`. (`Allow-Credentials: true` together with `*` is ignored by browsers, so cookies are not sent cross-origin.)
- **Caching:** no `Cache-Control`, `ETag` or `Last-Modified` was sent, so there is no server-provided caching hint. We would need our own TTL.
- **Tier:** `TODO`. **Behaviour for a deleted or unknown ID (status code, body):** `TODO`.
- **Still unknown:** whether the webhook body is this same object. Webhook details are in section 2.

Consequence for the Calendar page: signups can be fetched on demand by event ID with a plain GET, which is what the spec's "on-demand fetch" needs. Because the limits are per IP and generous for our scale but not unlimited, cache responses on our API (for example 30 to 60 s) rather than fetching once per page view. Because the endpoint is unauthenticated and public, anyone can also read it, so treat signup data (Discord user IDs and names) as already-public but avoid logging or re-exposing it beyond what the page shows.

### 3.3 Field notes
- **Timestamps are Unix seconds** (integers), confirming the guess in #31. `startTime` 1791331200 is 2026-10-07 00:00:00 UTC. `endTime - startTime` = 10800 s = `advancedSettings.duration` (180 min). `lastUpdated` equals the newest signup's `entryTime`.
- **`date` and `time` are display strings** in the event's timezone (here `"06-10-2026"`, DD-MM-YYYY, and `"18:00"`). The timezone is not in the object. Use `startTime`, not these.
- **Event `id` is a string**, a Discord snowflake (matches the message ID). Store as `text`, never parse as a number. This fits #31's `raid_helper_event_id text`.
- **No difficulty field.** Only `title`, `displayTitle`, `description` and `templateId` (`wowretail2`). #31's fallback of `'Unknown'` unless parseable from the title is right. The word "Normal" appears only in the free-text `description`.
- **`title` vs `displayTitle`** were identical here. Difference: `TODO`.
- **Signup `status` is not attendance.** Every signup is `"primary"`, including those who are Late or Tentative. Attendance state is carried by `className` (`Late`, `Tentative`, and by the template, `Bench` and `Absence`). For those signups the real role is in `roleName`, and `specName` is still the actual spec. For normal signups `className` is the role group (Tank/Melee/Ranged/Healer) and there is no `roleName`.
- **`c`-prefixed fields** (`cClassName`, `cSpecName`, `cRoleName`, `cName`) appear to be clean/canonical copies of the plain ones. Differences from the plain fields: `TODO`.
- **IDs:** signup `id` is a number, `userId` and all other Discord IDs are strings. `position` appears to be signup order (1..N), not a raid-slot position.
- **Display names are arbitrary user text**: they can contain quotes, emoji and parentheses. Always JSON-decode, never string-match.
- **Size:** the object is large because it embeds the whole class/spec template and ~100 settings. Only a handful of fields matter for the Calendar mirror.
- **The `image` URL is a signed Discord CDN link** that expires. Do not store it as a permanent asset URL.

## 4b. Fallback if webhooks are unavailable: polling the fetch endpoint
Based only on verified behaviour of `GET https://raid-helper.xyz/api/v4/events/{id}`:
- Store `raid_helper_event_id` for each mirrored raid, and refresh by fetching that ID. Use `lastUpdated` (Unix seconds) to skip unchanged events.
- Cache responses in our API for roughly 30 to 60 s. Rate limits (20/5 s, 100/min, 2,000/h per IP) are ample for that, but all visitors share the server's IP budget.
- Not solved: **discovering new event IDs**. The endpoint takes an ID, and no list-by-server endpoint has been found (`TODO`: check the docs and ask support). Without webhooks or a list endpoint, officers would have to paste the event ID or link into the site when creating a raid.
- A deleted event's response (status code and body) is unknown (`TODO`), which matters for detecting deletions.
