### 2.3 Authentication
**Scheme: shared secret in a header (VERIFIED, from the official docs' Webhooks > Authorization section, seen in a screenshot).**
- The webhook key (shown by `/webhooks show`, rotated by `/webhooks refresh-key`) is sent with each webhook request as a header named `Authorization`, with the key as the value. We compare it with our stored copy to confirm the request came from Raid-Helper.
- The docs call authorization "reversed and optional": it exists only so the receiver can verify the sender. Raid-Helper does not require us to check it, so **we must check it ourselves** or anyone who learns our URL can post fake events.
- One key per server, shared by all four webhook types (observed with `/webhooks show`).
- Success: the docs say any successful `200` response marks the webhook delivered. Behaviour on non-200 (retries, backoff, timeout): `TODO`.
- Not used (per the docs): no HMAC or body signature, no IP allowlist was mentioned. Whether the header value has a prefix such as `Bearer`: the docs say "the key as the value", so compare the whole header value to the raw key, `TODO` confirm on a real request.

### 3.1 Endpoint

### 3.3 Field notes
- **Timestamps are Unix seconds** (integers), confirming the guess in #31. `startTime` 1791331200 is 2026-10-07 00:00:00 UTC. `endTime - startTime` = 10800 s = `advancedSettings.duration` (180 min). `lastUpdated` equals the newest signup's `entryTime`.
- **`date` and `time` are display strings** in the event's timezone (here `"06-10-2026"`, DD-MM-YYYY, and `"18:00"`). The timezone is not in the object. Raid-Helper's Intro page says the bot needs to know the timezone in which date and time are entered when events are created on a server, so a per-server timezone setting exists (docs snippet, not independently tested). Use `startTime`, not these.
- **Event `id` is a string**, a Discord snowflake (matches the message ID). Store as `text`, never parse as a number. This fits #31's `raid_helper_event_id text`.
- **No difficulty field.** Only `title`, `displayTitle`, `description` and `templateId` (`wowretail2`). #31's fallback of `'Unknown'` unless parseable from the title is right. The word "Normal" appears only in the free-text `description`.
- **`title` vs `displayTitle`** were identical here. Difference: `TODO`.
- **Signup `status` is not attendance.** Every signup is `"primary"`, including those who are Late or Tentative. Attendance state is carried by `className` (`Late`, `Tentative`, and by the template, `Bench` and `Absence`). For those signups the real role is in `roleName`, and `specName` is still the actual spec. For normal signups `className` is the role group (Tank/Melee/Ranged/Healer) and there is no `roleName`.
- **`c`-prefixed fields** (`cClassName`, `cSpecName`, `cRoleName`, `cName`) were identical to their plain counterparts in all 16 signups and every class/spec entry of the sample (VERIFIED for this event). They may exist to hold the template's canonical names when a server has custom display names (`advancedSettings.alt_names` was `false` here), but that is `UNVERIFIED`. Safest for #31: read the `c` fields for matching against known specs, and treat the plain fields as display text.
- **IDs:** signup `id` is a number, `userId` and all other Discord IDs are strings. `position` appears to be signup order (1..N), not a raid-slot position.
- **Display names are arbitrary user text**: they can contain quotes, emoji and parentheses. Always JSON-decode, never string-match.
- **Size:** the object is large because it embeds the whole class/spec template and ~100 settings. Only a handful of fields matter for the Calendar mirror.
- **The `image` URL is a signed Discord CDN link** that expires. Do not store it as a permanent asset URL.

## 4b. Fallback if webhooks are unavailable (free tier): polling the fetch endpoint
Based only on verified behaviour of `GET https://raid-helper.xyz/api/v4/events/{id}`:
- Store `raid_helper_event_id` for each mirrored raid, and refresh by fetching that ID. Use `lastUpdated` (Unix seconds) to skip unchanged events.
- Cache responses in our API for roughly 30 to 60 s. Rate limits (20/5 s, 100/min, 2,000/h per IP) are ample for that, but all visitors share the server's IP budget.

## 5. Recommendations for #31
Based on the docs and the verified GET object. Not yet tested against a real webhook request.
- **Webhooks need Premium, and the team is purchasing it**, so build the receiver below. Polling (4b) is a fallback only. Premium price and whether it is per server or per user: `TODO`.
- **One endpoint per type:** `POST /api/webhooks/raid-helper/create`, `/update`, `/delete`. The bodies carry no `type`, so the path is the discriminator. Do not register `comp.update`.
- **Auth:** compare the request's `Authorization` header to the webhook key (constant-time compare, key from an env var such as `RAID_HELPER_WEBHOOK_KEY`). Reject with 401 on mismatch. The check is optional on Raid-Helper's side, so we must enforce it. Use the raw header value with no prefix handling; confirm on a real request.
- **One struct, one parser** for all three types (identical bodies). Upsert by `id` (`raid_helper_event_id text UNIQUE`). Parse `id` and other Discord IDs as strings.
- **Idempotent and fast.** `event.update` fires on every signup change. Return `200` quickly (the docs say `200` marks delivery successful; non-200 behaviour is undocumented). Use `lastUpdated` to ignore a stale, out-of-order delivery.
- **Delete:** use only `id` from the body; ignore the rest.
- **Fields to store:** `id`, `title`, `startTime`/`endTime`/`closingTime` (Unix seconds, `time.Unix(n, 0).UTC()`), `signUps` (or counts). Ignore `date`/`time` (display strings, no timezone). No difficulty field, default `'Unknown'`.
- Do not persist `advancedSettings.image` (signed, expiring Discord CDN link).
- Do not depend on `displayTitle`, `creator`, `announcements` (not listed in the webhook docs).
- Webhook key and API key are different secrets; keep both out of the repo.
